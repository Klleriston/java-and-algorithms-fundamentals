# Visual JVM and Algorithms Fundamentals — Design

Date: 2026-08-19
Status: Approved design, ready for implementation planning
Repository: https://github.com/Klleriston/java-and-algorithms-fundamentals

## 1. Purpose

An interactive web application that teaches Java fundamentals by showing them
running, step by step, instead of describing them in prose. Two families of
content share one architecture:

- **Data structures and algorithms** — binary search, bubble sort, binary tree,
  `HashSet`. The learner supplies an input, presses Run, and watches the
  structure change while the corresponding line of Java is highlighted.
- **JVM internals** — the memory model (stack frames, heap objects, metaspace)
  and garbage collection (generations, promotion, collection pauses).
- **Object-oriented programming** — inheritance, polymorphism, and
  encapsulation, shown as they behave at runtime: which constructor runs when,
  which method implementation the JVM actually selects, and what access
  modifiers protect.

Everything on the algorithm side is real Java executed on the server. The GC
module runs a real child JVM and reports measured numbers, not an animation.

The audience is Java developers. All example code is Java, and the explanations
assume Java vocabulary.

## 2. Goals and non-goals

### Goals

- Every demo shows Java source with the currently executing line highlighted.
- Every demo exposes parameters the learner controls (array contents, search
  target, heap size, collector).
- The visualization is a player: play, pause, step forward, step back, scrub,
  adjust speed.
- Adding a new demo means adding one backend class and, if the visual form is
  new, one frontend renderer. No existing code changes.
- Numbers presented as measured must actually be measured.

### Non-goals for this project

- Running arbitrary user-supplied Java. The learner changes parameters of
  curated demos; there is no code editor and no sandbox to build.
- WebSocket streaming. A trace is returned whole, in one response.
- Accounts, authentication, persistence, or any database.
- Internationalization. The UI ships in one language.

## 3. Architecture

### 3.1 Repository layout

```
backend/          Spring Boot 3 (Java 21), Maven
  pom.xml
  src/main/java/.../core/      algorithms and demo implementations
  src/main/java/.../trace/     Tracer, Trace, TraceStep, view payloads
  src/main/java/.../jvm/       child JVM runner and GC log parser
  src/main/java/.../api/       REST controllers, DTOs, validation
frontend/         React 18 + TypeScript + Vite
  src/components/  CodePanel, renderers (ArrayView, TreeView, ...)
  src/hooks/       useTracePlayer
  src/fixtures/    golden traces generated by the backend, used in tests
docs/superpowers/specs/
.github/workflows/ci.yml
```

`.superpowers/` (visual brainstorming artifacts) is gitignored.

### 3.2 Backend layers

Three layers with one-directional dependencies: `api` → `core` → `trace`.

- **`trace`** — the data model. `Tracer` collects `TraceStep`s, enforces the
  step cap, and produces an immutable `Trace`. Knows nothing about any specific
  algorithm and nothing about HTTP.
- **`core`** — the demos. Each algorithm is written the way it would be written
  in a textbook, taking a `Tracer` as a parameter and calling it at the points
  that matter. No HTTP, no JSON, no Spring.
- **`jvm`** — the second trace producer, for the GC demo. Spawns a child JVM,
  parses its GC log, and emits the same `Trace` type.
- **`api`** — controllers, request validation, and mapping `Trace` to JSON.

### 3.3 Demo registry

Each demo registers itself as a Spring bean implementing `Demo`:

```java
public interface Demo {
    String id();                      // "binary-search"
    String title();
    Category category();              // ALGORITHMS | DATA_STRUCTURES | JVM | OOP
    String description();
    List<ParameterSpec> parameters();  // drives the frontend form
    String displaySource();            // clean Java source shown to the learner
    Trace run(Map<String, Object> params);
}
```

`DemoRegistry` collects every `Demo` bean by id. Controllers never name a demo,
so adding one requires no controller change. `displaySource()` returns source
without `tracer.step(...)` calls; steps carry the line number in that clean
source, which is what the frontend highlights.

## 4. Trace model

The trace is the contract between backend and frontend. It has a fixed part
that every step carries and a view payload that varies by visual form.

```json
{
  "demoId": "binary-search",
  "title": "Binary Search",
  "sourceCode": "public static int search(int[] a, int target) { ... }",
  "steps": [
    {
      "index": 4,
      "line": 7,
      "message": "mid = 3, a[mid] = 12 < 20, discard the left half",
      "vars": { "low": 4, "high": 5, "mid": 3 },
      "view": {
        "kind": "ARRAY",
        "items": [2, 5, 8, 12, 20, 33],
        "pointers": { "low": 4, "mid": 3, "high": 5 },
        "ranges": [{ "from": 0, "to": 3, "state": "DISCARDED" }]
      }
    }
  ],
  "result": { "returnValue": 4, "stepCount": 5, "measured": false }
}
```

Fixed on every step: `index`, `line`, `message`, `vars`. These alone drive the
code panel and the variable table, for any demo of any kind.

`result.measured` is `true` when the numbers came from a real JVM measurement
(the GC demo) and `false` otherwise. The UI shows a "measured on a real JVM"
badge only when it is `true`.

### 4.1 View kinds

The frontend maps `view.kind` to a renderer component. An unknown kind falls
back to a renderer that shows only line, message, and variables, so a backend
that ships a new kind first never breaks the page.

| Kind | Used by | Payload |
|---|---|---|
| `ARRAY` | binary search, bubble sort | `items`, `pointers` (name → index), `ranges` (`from`, `to`, `state`: `DISCARDED` \| `SORTED` \| `ACTIVE`), `swapped` (pair of indices, optional) |
| `TREE` | binary tree | `nodes` (`id`, `value`, `left`, `right`), `rootId`, `currentId`, `visitedIds`, `pathIds` |
| `HASH_TABLE` | hashset | `capacity`, `loadFactor`, `buckets` (`index`, `entries`: `key`, `hash`, `state`), `currentBucket`, `resizing` |
| `MEMORY` | jvm-memory, inheritance, encapsulation | `frames` (`method`, `slots`: `name`, `value` or `refId`), `objects` (`id`, `type`, `fields`, `reachable`), `metaspaceClasses`. Each field carries `visibility` (`PRIVATE` \| `PROTECTED` \| `PUBLIC` \| `PACKAGE`) and an optional `access` marker (`ALLOWED` \| `REJECTED`) so encapsulation steps can show a blocked access |
| `CLASS_HIERARCHY` | polymorphism, inheritance | `classes` (`name`, `superName`, `methods`: `signature`, `declared`, `overrides`, `abstract`), `declaredType`, `runtimeType`, `invokedSignature`, `resolvedIn` (class whose implementation runs), `lookupPath` (classes walked during dispatch) |
| `GC` | gc | `collector`, `pools` (`name`: `EDEN` \| `SURVIVOR_0` \| `SURVIVOR_1` \| `OLD` \| `METASPACE`, `usedBytes`, `capacityBytes`), `event` (`type`: `MINOR` \| `MAJOR`, `cause`, `pauseMillis`, `beforeBytes`, `afterBytes`), `uptimeMillis` |

### 4.2 Parameter schema

`GET /api/demos` returns each demo's `ParameterSpec` list, and the frontend
builds the input form from it. Nothing about any specific demo is hardcoded in
React.

```json
{
  "name": "array",
  "type": "INT_ARRAY",
  "label": "Sorted array",
  "required": true,
  "maxLength": 512,
  "defaultValue": [2, 5, 8, 12, 20, 33]
}
```

Types: `INT`, `LONG`, `INT_ARRAY`, `STRING_ARRAY`, `ENUM` (with `options`).
Numeric types carry `min` and `max`; array types carry `maxLength`; `ENUM`
values are validated against `options` server-side.

## 5. API

```
GET  /api/demos                 → 200: [DemoSummary]  (id, title, category,
                                        description, parameters, sourceCode)
POST /api/demos/{id}/trace      → 200: Trace
                                  400: { "error", "message", "field" }
                                  404: unknown demo id
                                  503: GC runner busy or unavailable
```

The server is stateless. Play, pause, step back, and scrubbing are pure client
state changes over a trace already in memory; only Run issues a request.

## 6. Trace producers

### 6.1 In-process tracer (all demos except GC)

The demo calls `tracer.step(line, message, vars, view)` at the points worth
seeing. Deterministic, fast, and fully under our control. The step cap (10,000)
is enforced inside `Tracer`; exceeding it aborts the run with a 400 rather than
returning a silently truncated trace.

### 6.2 Child JVM runner (GC demo)

The GC demo measures a real JVM:

1. Spawn `java` from the running `JAVA_HOME` with flags assembled from
   validated parameters: `-Xmx`, `-Xms`, a collector flag, and
   `-Xlog:gc*:file=<temp>:time,uptime,level,tags`.
2. The child runs a bundled workload class chosen by an `ENUM` parameter
   (for example, short-lived allocations, surviving allocations, mixed).
3. On exit, parse the unified GC log into `GC` view steps.
4. Delete the temp directory.

Safety and resource rules, all mandatory:

- **No string passes from the request to the command line.** Collector and
  workload are enums mapped to fixed flag constants; heap size is an integer
  validated against a range and formatted by the server.
- Hard timeout (20 seconds), then `destroyForcibly`.
- One concurrent child JVM process, guarded by a semaphore; a second request
  gets 503 with a retry message.
- Output size cap; the child inherits no network access requirement and runs in
  a temp working directory.
- The child never executes user-supplied code — only bundled workload classes.

The runner is deliberately behind an interface so the frontend is unaffected if
the measurement mechanism changes (for example, to JFR) later.

## 7. Frontend

Two routes:

- `/` — catalog, grouped by category, built from `GET /api/demos`.
- `/demo/:id` — the demo screen. Parameters live in the query string
  (`?array=2,5,8,12,20,33&target=20`), so a run is a shareable link and a reload
  restores it.

The demo screen is a resizable split pane in the style of LeetCode, dark theme:

- **Left** — Java source, monospace, line numbers in the gutter, the active line
  highlighted. Read-only.
- **Right, top** — the renderer selected by `view.kind`.
- **Right, bottom** — the variable table (`vars`) and the step `message`.
- **Top** — the parameter form generated from the demo's schema, plus Run.
- **Bottom** — transport controls: first, previous, play/pause, next, last; a
  scrub bar; a speed selector; a `step 4 / 7` counter.

Three independently testable pieces:

- `useTracePlayer` — owns `currentStepIndex`, play/pause, the timer, and
  boundary behavior. Knows nothing about the DOM.
- `CodePanel` — takes source and an active line.
- Renderers (`ArrayView`, `TreeView`, `HashTableView`, `MemoryView`, `GcView`) —
  each takes one view payload. Registered in a `kind → component` map; adding
  one touches no existing renderer.

Request failures (400, 500, network) render as an inline banner carrying the
server's message. The previously loaded trace stays on screen.

## 8. Validation, limits, and errors

Validation lives in the backend; the frontend only displays messages.

- Binary search rejects an unsorted array: `array must be sorted ascending`.
- Array length ≤ 512; values within `int` range.
- Step cap 10,000 per trace.
- Execution timeout: 5 seconds in-process, 20 seconds for the child JVM.
- GC heap size constrained to a documented range; collector and workload must
  match their enum options.

Every rejection is a 400 with `error`, human-readable `message`, and the
offending `field` when applicable.

## 9. Testing

### Backend (JUnit 5, Maven Surefire)

- **`core`** — correctness independent of tracing: binary search finds the
  index, returns `-1` when absent, handles empty and single-element arrays;
  bubble sort sorts; tree insert/search/traverse; hashset add, contains,
  collision, resize.
- **`trace`** — `Tracer` enforces the step cap; `Trace` is immutable.
- **`api`** — MockMvc: `GET /api/demos` returns schemas; valid parameters return
  200 with steps; unsorted array returns 400 with the message; oversized array
  returns 400; unknown demo id returns 404.
- **`jvm`** — the GC log parser is tested against committed sample log files, so
  parser tests need no child process. One integration test, tagged and runnable
  separately, spawns a real child JVM and asserts that at least one collection
  was parsed.
- **Golden tests** — a fixed input produces an exact step sequence per demo.
  This is what locks the JSON contract.

### Frontend (Vitest, React Testing Library, MSW)

- `useTracePlayer` — advances, steps back, clamps at both ends, and advances
  under play with fake timers.
- `CodePanel` — highlights the expected line.
- Each renderer — draws its payload's distinguishing features (pointers and
  discarded ranges; visited nodes; bucket collisions; pool fill levels).
- API calls mocked with MSW using fixtures **generated by the backend golden
  tests** and committed to `frontend/src/fixtures`. When the backend contract
  changes, the stale fixture makes the divergence fail loudly instead of
  drifting silently.

### CI

GitHub Actions on push and pull request: `mvn -B verify` and `npm ci && npm test
&& npm run build`. The child-JVM integration test runs in CI; it is excluded
from the default local run.

## 10. Delivery phases

One architecture, delivered in four phases. Each phase ends with a working,
deployable app.

**Phase 1 — pipeline and `ARRAY`**
Backend skeleton, trace model, `Tracer`, demo registry, both endpoints,
`binary-search` and `bubble-sort`. Frontend skeleton, catalog, demo screen,
`useTracePlayer`, `CodePanel`, `ArrayView`. Tests and CI. Two demos, not one:
the second proves that a renderer generalizes and that a new demo is one class.

**Phase 2 — `TREE` and `HASH_TABLE`**
`binary-tree` (insert, search, in-order traversal, with visited nodes and the
current path highlighted) and `hashset` (`hashCode`, bucket index, collision,
`equals`, resize with rehash — the part that most often confuses Java
developers). Two backend demos, two frontend renderers.

**Phase 3 — `MEMORY` and `GC`**
`jvm-memory` (stack frames versus heap objects, references, metaspace, what
becomes unreachable when a frame pops) via the in-process tracer, and `gc` via
the child JVM runner with measured pool sizes and pause times. The learner picks
heap size, collector, and allocation workload, and can compare collectors.

**Phase 4 — OOP**
Three demos and one new renderer.

- `inheritance` — constructor chaining. A `new Dog()` walks up to `Object` and
  back down; the `MEMORY` view shows the single object growing its inherited
  fields while the `CLASS_HIERARCHY` view shows where each constructor lives.
  Field shadowing is included, because it is where the mental model usually
  breaks: fields resolve by declared type, methods by runtime type.
- `polymorphism` — dynamic dispatch. `Animal a = new Dog(); a.speak();` The
  `CLASS_HIERARCHY` view marks the declared type, the runtime type, and the
  lookup path the JVM walks to find the implementation that runs. Compares an
  overridden method with a `static` method, which does not dispatch dynamically.
- `encapsulation` — a class with an invariant (a balance that must never go
  negative). Mutating through the method is accepted and the invariant holds;
  the step showing a direct field write is marked `REJECTED` with the compiler
  error text, making visible what `private` actually buys.

Backend work is three `Demo` classes on the existing in-process tracer. Frontend
work is one new renderer, `ClassHierarchyView`, plus extending `MemoryView` to
draw field visibility and access markers.

## 11. Future work, explicitly out of scope now

- A code editor with a real sandbox for arbitrary Java.
- Additional JVM topics: JIT compilation tiers, class loading order, bytecode
  disassembly.
- More algorithms (merge sort, graph traversal, dynamic programming).
- Replacing GC log parsing with JFR event streaming.
- Deployment: the first target is local development; hosting is decided after
  Phase 1.
